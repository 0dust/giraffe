# Workload and deployment validation on October 8, 2026

This validates the issue #2 workload expansion and issue #3 deployment/telemetry
capture against two real local serving runtimes, plus deterministic loopback
tests for failure modes that cannot be safely induced on the live servers.
All ten core checks and all seven additional checks were selected for each full
run. JSON and GPU checks were not selected. Endpoint failures remain recorded;
passing the implementation checks does not turn a failed endpoint into an approved deployment.

## Runtime setup

The test generator ran on an Apple M1 Mac with 8 GB RAM. The models ran separately.
The existing Ollama daemon was preserved; task-loaded models were unloaded after
each run. Task-owned vLLM server process groups were stopped after each run.
The supervisor sampled `kern.memorystatus_vm_pressure_level` every 250 ms,
required normal pressure at startup, and would stop task-owned processes at
critical pressure. No critical sample was observed.

| Runtime | Model and identity | Serving setup |
| --- | --- | --- |
| vLLM 0.30.0 with vLLM-Metal 0.30.0 and MLX 0.32.1 | Llama 3.2 1B Instruct, 4-bit; local checkpoint revision `08231374eeacb049a0eade7922910865b8fce912` | `127.0.0.1:8000/v1`; context 1,024; maximum sequences 2; batch-token cap 64; block override 128; memory utilization 0.30; eager; prefix caching disabled; automatic tools with `llama3_json` parser |
| Ollama 0.12.10 | `llama3.2:3b`, Q4_K_M; digest `a80c4f17acd55265feec403c7aef86be0c25983ab279d83f3bcd3abbcb5b8b72` | Existing `127.0.0.1:11434/v1`; active context 4,096 reported by `/api/ps` |

Runtime versions are API-reported. Model revision and vLLM launch settings are
user-supplied setup facts, preserved with that provenance. Ollama digest and
active context also have runtime-reported discovery evidence. No target hardware
was inferred from the generator. This qualifies vLLM through its Metal plugin;
Linux/CUDA vLLM remains untested. The models differ, so these runs cannot isolate
an engine performance difference.

## Traffic and reproduction

The [vLLM configuration](2026-10-08-vllm.json) and
[Ollama configuration](2026-10-08-ollama.json) preserve the tested traffic and
acceptance settings. Their metadata-file paths are relative to the repository
root; accompanying metadata exports preserve source scope and collection time.
These exports describe the tested setup and must be updated for another deployment.

From the repository root, with the corresponding model/server already running:

```sh
giraffe run --config docs/validation/2026-10-08-vllm.json --output runs/vllm-expanded
giraffe run --config docs/validation/2026-10-08-ollama.json --output runs/ollama-expanded
giraffe inspect runs/vllm-expanded/report.json
giraffe export runs/vllm-expanded/report.json > reproduction.json
```

Each run allows concurrency 2, 700 requests, 1,800 seconds, 120 seconds/request,
and 128 output tokens/request. Core samples are 6; sustained traffic is 30 seconds.
The configured limits are first output 60 seconds, latency 90 seconds, stream gap
10 seconds, minimum generation pace 1 token/second, no request errors, correctness
1.0, mixed latency ratio 3, and minimum successful samples 5.

Additional traffic selects 12 burst arrivals (2 per second), 256-character prefixes
with 6 shared/control trials and 3 fixed-history turns, all 18 length/load cells
(64/256/512 input characters, 24/64/128 output ceilings, concurrency 1/2, 6 samples),
both heavy shapes before output and during streams (6 pairs), 2 fixed and 2 live
sessions with 50 ms requested turn delay, 6 consistency repetitions for short/long
inputs at concurrency 1/2, and automatic complete/streamed tool calls plus separate
forced diagnostics. Requested characters and ceilings are distinct from observed
token lengths. Automatic tool calls are parsed and scored; no tool is executed.

## Results and coverage

Two additional fix/validation cycles completed within the three-cycle limit.
Cycle one ran 504 vLLM requests and 416 Ollama requests. It exposed inappropriate
hexadecimal prefix controls, while review identified sample/overlap qualification
and generator-lag inconsistencies in the new checks. Cycle two uses ordinary prose
controls, consistent timing qualification, qualified mixed-load ratios, explicit
coverage gaps, and source-bound workload fixture identity. Endpoint scorers and
acceptance limits were preserved.

The final code passed **307 automated tests in 22.92 seconds**, Ruff, JavaScript
syntax validation and `git diff --check`. Source fingerprints were checked against
both completed live runs. No code changed while those runs were active.
The final local UI was reloaded and checked for failed-answer evidence, the
fixture-incompatible baseline, deployment history and reproduction export.

Final vLLM run: **502 requests in 225.94 seconds**, 24.122 ms maximum generator
lag. Final Ollama run: **416 requests in 498.51 seconds**, 45.018 ms maximum lag.
Neither run aborted. JSON/GPU checks were skipped explicitly. The recorded endpoint
outcomes remain `fail` for vLLM and `inconclusive` for Ollama; they are not approved
deployment baselines. The CLI returned 1 and 2 respectively for those outcomes.

The vLLM checkpoint answered `Blue, green, and purple` for the stop fixture
`Copy exactly, with no extra text: blue [END] green` with stop token `[END]`.
All three stop samples failed the unchanged expected answer `blue`. In fixed
sessions it returned `Golden Crust Bakery` when asked to repeat saved `Golden Crust`;
live exact-repeat responses also changed punctuation. These are valid answer-check
failures, rather than evidence that backend cancellation or the serving engine is broken.

Both runtimes left `short`-input/`medium`-output and `short`-input/`long`-output cells
at concurrency 1 and 2 inconclusive because too few answers reached half the
requested output ceiling. All 18 cells were dispatched, with actual lengths and
finish reasons retained. Giraffe did not force generation after EOS to fill a bucket.
All four mixed comparisons had enough control/load samples and achieved overlap;
none exceeded the configured ratio of 3.

vLLM published 114 usable serving snapshots. Cache occupancy peaked at 37.8%; the
90% pressure regime was **not exercised**. Prefix-hit and preemption deltas were
zero for the observed label scope. Untimestamped source freshness and other shared
traffic remain unknown; those counters do not certify physical cache behavior.
Ollama had no configured serving-metrics URL and correctly reported `no_endpoint`,
without claiming disabled instrumentation or healthy scheduling. Its end discovery
snapshot captured active context 4,096 and the matching model digest.

Both explicit baseline comparisons rejected metric comparison because fixture
identity changed, while keeping deployment diffs, telemetry and reference failure
outcomes visible. No deployment change was observed between available snapshots;
continuity between samples and other replicas remain unverified.

and fragmented tool calls, absent cache usage, early EOS, budgets and cancellation.
Deployment tests cover manual/imported/reported provenance, conflicts, stale data,
mid-run changes, secret exclusion, legacy baselines, immutable failed references,
workload incompatibility with visible deployment diffs, and confounded experiments.
Telemetry tests cover empty/absent/auth/unsupported/stale responses, gauge peaks,
counter resets, label changes, bounded collection and missing instrumentation evidence.
