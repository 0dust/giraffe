## Necessary fixes

- Inactive dataset fields (`expected_provided=false`, `rubric=null`) no longer
  change the built-in fixture fingerprint. Active fields remain included. The
  existing legacy-fingerprint regression caught this after the rebase.
- Metrics client/CA setup runs in a worker thread. HTTPX creates a TLS context
  even for an HTTP metrics URL; doing this synchronously inside each periodic
  scrape can block inference scheduling. The new regression blocks setup and
  requires an independent inference coroutine to continue. It failed before the
  fix and passes afterward. TLS validation, headers, proxy, redirect policy and
  scrape deadlines are retained.

The heartbeat threshold and all answer/performance acceptance rules are unchanged.
The existing run-wide maximum-based timing qualification remains unchanged.

## Runtime and model controls

Apple M1, macOS 15.5, 8 GB unified memory. Only one trial inference server was
loaded at a time, in this order: Ollama, unload/stop, vLLM, stop, SGLang, stop.
The original Ollama daemon on port 11434 and its model store were preserved.
Trial ports were checked closed between engines. Memory guards sampled macOS
pressure every 250 ms and would stop the owned server group at critical pressure.

All three used the same source checkpoint:
`mlx-community/Llama-3.2-1B-Instruct-4bit`, revision
`08231374eeacb049a0eade7922910865b8fce912`, source weight SHA-256
`35e396644bca888eec399f9c0f843ec7fa78b8f8c5e06841661be62b4edf96dd`.
SGLang/vLLM read the same MLX files. Ollama used the existing chunked F16
expansion/import of those 146 tensors, retaining their quantized values rather
than downloading another checkpoint or requantizing them. Its GGUF weight layer
SHA-256 is `02a53ad2f722fe9ab7e0c94152a9b011c370843037b47a263e14d8c76bb9dba5`.
This does not recover the original model's pre-quantization precision.

- Ollama 0.12.10, isolated store/port 11435, one runner slot, repetition penalty 1.
- vLLM 0.30.0 / vllm-metal 0.30.0, port 8000, two sequences, native scheduler
  cancellation observer. That observer disables asynchronous scheduling.
- SGLang source `44bc478863052efdc455b0282b49830f68fdefb3`, MLX backend,
  port 30000, two running requests, metrics, xgrammar and native OTLP traces.

All contexts were 1024 tokens, temperature zero. Final trials fixed the template
metadata date to 12 Oct 2026 so crossing midnight would not alter prompts.
Tool schema serialization still differs between the native Ollama Go template
and the Hugging Face template. These are deployment validation runs, not a fair
engine throughput ranking; concurrency and numerical backends differ.

The first Ollama trial returned tool JSON as plain text. Its custom template did
not declare the emitted `<|python_tag|>` tool prefix. Ollama's version-matched
[generic parser](https://github.com/ollama/ollama/blob/v0.12.10/tools/tools.go)
stops JSON-only tool detection when non-whitespace text precedes the first `{`;
the [template inference](https://github.com/ollama/ollama/blob/v0.12.10/tools/template.go)
falls back to `{` without a tool tag. Adding a `.ToolCalls` template branch with
that prefix fixed all four focused automatic/forced, streaming/non-streaming
probes before the final full run. No Giraffe parser or scorer was changed.

## Measured scheduling cause

The pre-fix vLLM full run captured one heartbeat over 100 ms out of 10,805 samples
(0.0093%). At 372.38 seconds, during `bucket_c2_medium_medium`, heartbeat lateness
was 180.95 ms. The same interval recorded:

- HTTPX `AsyncClient` construction: 166.84 ms wall time, 15.29 ms thread CPU.
- Metrics sampler callback: 175.42 ms wall time, 22.78 ms thread CPU.
- macOS memory pressure: normal (level 1).

This directly identifies a synchronous metrics setup operation blocking Giraffe's
event loop. The long wall time includes time not spent executing Python; the
capture does not identify the OS reason for that wait. Critical RAM pressure was
not observed, and resource exhaustion is not established as the cause.

One spike caused nine checks to become timing-inconclusive, plus the independently
unavailable GPU check: 6 pass, 3 fail, 10 inconclusive. This demonstrates how rare
client delays can create many inconclusive check results. Earlier reports retained
only the maximum, so their spike frequency and exact causes cannot be reconstructed.
The first Ollama trial had 0/15,799 heartbeats over 100 ms (maximum 79.58 ms).

Final diagnostics record every 50 ms heartbeat, active scenario, thread CPU,
pressure and slow synchronous callbacks/client construction. This instrumentation
is external to the product and did not change scoring. Diagnostic file writes add
small overhead; results describe these controlled trials, not a long-term rate.

## Failure and coverage analysis

### Reproduced answer failures

All three runtimes produced the same failures with the shared source checkpoint:

- Capacity: all 12 `traffic.long_output.v1` colour-copy requests returned a refusal
  about a colour pattern being obscene or off-putting, rather than the requested
  copy. The prompt contains harmless colour words; the reason the model chose
  this refusal is unknown. This is a genuine fixture-answer mismatch, not an
  established serving failure.
- Limits: `limits.stop.v1` returned `Blue ` rather than expected lowercase `blue`.
  The direct SGLang response records `finish_reason=stop` and `matched_stop=[END]`.
  Stopping worked; the exact-answer criterion failed. This fixture still mixes
  copying/case fidelity with stop handling, a previously identified test-design
  limitation.
- Fixed sessions: both responses changed `Golden Crust` to `Golden Crust Bakery`.
- Live sessions: both repeat responses included the original `Sweet Delights
  Bakery` plus four extra names: Bakehouse Bliss Bakery, Flour & Fancy Bakery,
  The Sweet Spot Bakery and Cupcake Cove Bakery.

Direct HTTP controls against SGLang reproduced the colour refusal, case change
and fixed-session addition, bypassing Giraffe's response parsing. Identical
answer failures across all three runtimes support a shared model/prompt problem;
they do not establish a universal defect in any inference engine. Acceptance
rules were not relaxed to hide these outputs.

### Cancellation evidence remains separate from answers

| Runtime | Verify server stopped | Native termination / slot reuse after client cancellation | Verify answer |
| --- | --- | --- | --- |
| Ollama | Inconclusive; capacity release 3/3 | Exclusive slot reused in 133.95, 133.35, 351.69 ms | Fail: 3/4 correct |
| vLLM | Pass: matching native abort 3/3 | 13.66, 13.73, 13.16 ms | Fail: 3/4 correct |
| SGLang | Pass: matching native abort 3/3 | 45.61, 61.80, 60.99 ms | Fail: 3/4 correct |

All follow-up inference responses were valid. Ollama's isolated slot and cache
observations demonstrate capacity release, not a native abort reason or exact
termination time. Its cancelled cache grew only 5, 5 and 7 tokens versus each
128-token uncancelled reference. Its server-stop verdict correctly stays
inconclusive. Neither native abort evidence nor slot reuse proves physical GPU
memory deallocation. The answer failure in every runtime is the independent
`Blue` mismatch, not the interrupted partial response.

### SGLang forced-tool diagnostic

Automatic tool calls passed in all three engines. SGLang's two forced-tool
probes returned HTTP 200 with a parsed `get_weather` call and empty arguments
`{}`, failing the required-city diagnostic.

A focused direct HTTP control requested output token log probabilities. Its token
sequence explicitly contains `"arguments":{}`: the city was not lost by Giraffe
or SGLang's response parser. Default/non-strict and explicit `strict=false`
requests both produced `{}`; the same control with `function.strict=true`
produced `{"city":"Delhi"}`.

The installed SGLang source explains the constraint: for the `llama3` parser,
`FunctionCallParser.get_structure_constraint` chooses the legacy structural tag
for a named tool. `get_legacy_structural_tag` supplies the argument schema only
when the function is strict (or the server's parameter-strict setting is on);
otherwise it supplies an empty schema. The function call is constrained, but
correct argument selection is left to the model. This explains how the empty
arguments are permitted; it does not explain the model's internal reason for
choosing them. The earlier native JSON-schema comparison used a different prompt
and constraint, so it is not evidence of an OpenAI response-parsing bug.

These are deployment/model diagnostics, not a reason to silently enable strict
mode in Giraffe or change its scorer. The final full-run results retain both
forced diagnostic failures.

### How often the final heartbeat was late

| Runtime | Heartbeats sampled | Lateness >100 ms | Maximum lateness | p95 lateness |
| --- | ---: | ---: | ---: | ---: |
| Ollama | 15,608 | 1 | 106.13 ms | 2.24 ms |
| vLLM | 10,737 | 1 | 105.49 ms | 2.18 ms |
| SGLang | 6,937 | 1 | 104.08 ms | 2.17 ms |

That is **3/33,282 samples (0.0090%)** over 100 ms in the final full runs. It is
an observed rate for these runs, not a forecast or a long-term estimate.

The peaks occurred during Ollama's fixed session and vLLM/SGLang's bucket
workloads. Thread CPU during those late heartbeat intervals was respectively
0.22, 0.91 and 2.54 ms, with normal macOS pressure at all three peaks. No long
synchronous callback/client construction overlapped the Ollama/vLLM peak.
SGLang's selector diagnostics recorded late OS poll returns near its peak
(e.g. a 45 ms return for a 17 ms requested wait). A separate 50 ms poll returned
in 133.51 ms while using only 0.02 ms thread CPU.

These residual delays are consistent with late OS polling/process wake-ups,
not demonstrated synchronous Python work. The exact OS cause is unresolved:
CPU sharing, paging and other scheduling effects cannot be distinguished from
these observations. Normal pressure at the peak does not rule out paging.
Ollama/SGLang did have some warning-pressure samples elsewhere; no critical
pressure occurred during startup, execution or cleanup. Existing swap was about
2.6 GiB before these final trials, so it cannot be attributed to them.

The confirmed metrics setup blocking no longer runs on the inference event loop.
However, the current grader uses one maximum heartbeat value for the entire run.
Consequently, each rare peak made nine checks inconclusive, even checks whose
active request intervals had no >100 ms sample. This yields **27 timing
inconclusives from three peaks**, plus three missing-GPU results. Active-request
interval analysis is diagnostic only: it does not cover between-request dispatch
gaps and is not sufficient to replace the grader safely.

No threshold was increased and no report was manually reclassified. Per-workload
scheduling qualification remains a separate design issue. These results do not
establish that the endpoint failed all nine timing requirements, and they also
do not qualify those requirements as passing.

### Raw mixed-load measurements

Despite the global inconclusive verdict, reports retain useful observations.
Ollama's short-request latency ratio with a long output before first output was
20.90x versus the configured 3.0x requirement, consistent with queuing in its
single-slot deployment. vLLM's long-input ratios were 3.31x before output and
3.16x during an active stream. SGLang's four ratios were 1.30–1.48x. Sample and
overlap requirements were met for these comparisons, but the run-wide timing
qualification prevents treating them as final pass/fail attribution. These
controls cannot rank engines fairly given different runner concurrency.
