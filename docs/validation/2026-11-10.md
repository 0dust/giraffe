# Linux GPU validation on November 10, 2026

> **Scope.** This records Giraffe main at `b58fe37` (package version 0.1.0a1)
> against vLLM and Ollama on one Linux machine with NVIDIA Tesla T4 GPUs. It does
> not cover other engines, other GPU generations, multi-GPU serving, Docker or the
> `release/0.1` branch. The [October 8 record](2026-10-08.md) remains historical
> and is not replaced by this one.

[Documentation index](../README.md)

## Runtime setup

The test generator and both engines ran in one Kaggle notebook session: Ubuntu
24.04.4, Linux 6.18.55, 4 vCPU, 31 GB RAM and two Tesla T4 GPUs (15,360 MiB each,
compute capability 7.5) on NVIDIA driver 580.178.04. Giraffe was installed from
commit `b58fe37bf28338feb25df0a04fc5fb6c968eefe4` into a Python 3.12.3 virtual
environment. vLLM ran on GPU 0 and was stopped before Ollama started on GPU 1.

| Runtime | Model and identity | Serving setup |
| --- | --- | --- |
| vLLM 0.33.0 with PyTorch 2.14.0 and CUDA 13.0 | `Qwen/Qwen2.5-1.5B-Instruct`, revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, float16 | `127.0.0.1:8000/v1`; `--dtype half --max-model-len 4096 --gpu-memory-utilization 0.85 --enable-prompt-tokens-details`; other settings at their defaults |
| Ollama 0.40.16 | `qwen2.5:1.5b`, Q4_K_M; digest `65ec06548149b04c096a120e4a6da9d4017ea809c91734ea5631e89f96ddc57b` | `127.0.0.1:11434/v1`; default settings; context 4,096 reported by `/api/ps` |

Runtime versions are API-reported (`/version` for vLLM, `/api/version` for
Ollama). The vLLM revision was pinned at launch; the Ollama digest comes from
`/api/tags`. The models differ in precision and serving stack, so these runs
cannot isolate an engine performance difference.

## Traffic and reproduction

The [vLLM configuration](2026-11-10-vllm.yaml) is `examples/vllm.yaml` with the
endpoint and served model filled in. The
[Ollama configuration](2026-11-10-ollama.yaml) names only the endpoint and model;
it was not derived from `examples/local.yaml` and sets no `metrics_profile`. The
engines were started with:

```sh
CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen2.5-1.5B-Instruct \
  --revision 989aa7980e4cf806f80c7fef2b1adb7bc71aa306 --dtype half \
  --max-model-len 4096 --gpu-memory-utilization 0.85 \
  --enable-prompt-tokens-details --host 127.0.0.1 --port 8000

CUDA_VISIBLE_DEVICES=1 OLLAMA_HOST=127.0.0.1:11434 ollama serve
ollama pull qwen2.5:1.5b
```

Both runs selected the same checks. The commands are shown with repository paths;
the notebook read the configurations from, and wrote the reports to, its working
directory:

```sh
giraffe run --config docs/validation/2026-11-10-vllm.yaml \
  --checks access,serving,correctness,first_output,generation,load,gpu,prefix,json,cancellation \
  --max-duration 1500 --output runs/vllm --html
giraffe run --config docs/validation/2026-11-10-ollama.yaml \
  --checks access,serving,correctness,first_output,generation,load,gpu,prefix,json,cancellation \
  --max-duration 1200 --output runs/ollama --html
```

Every other setting kept its default: a 300-second request timeout, a 128-token
default output cap that the built-in fixtures and Load test workloads replace with
their own (Load requests used 64 or 512), and the default Load test of 12
conditions (short/short, long/short and short/long workloads at concurrency 1 and 4
and at constant arrival rates of 1 and 2 requests per second). Its pass criteria
were a 2,000 ms first answer, a 30,000 ms completion, no errors, every answer
correct and at least five valid responses per condition.

`giraffe export` snapshots of both runs are saved as the
[vLLM export](2026-11-10-vllm-export.json) and the
[Ollama export](2026-11-10-ollama-export.json). Their paths point at the notebook's
working directory. The full JSON and HTML reports are not committed.

## Results and coverage

| Check | vLLM 0.33.0 | Ollama 0.40.16 |
| --- | --- | --- |
| Endpoint access | Pass | Pass |
| Response validity | Pass | Pass |
| Time to first answer | Pass | Pass |
| Generation speed | Pass | Pass |
| Answer correctness | Pass | **Fail: 5/6, answered `T8R2. Blue` for `T8R2`** |
| JSON correctness | Pass | Pass |
| Load test | **Fail: 2 of 12 conditions over a timing limit** | **Fail: 4 of 12 conditions over a timing limit** |
| Cancellation & limits | **Fail: exact-copy fixture paraphrased (3/3)** | **Fail: exact-copy fixture paraphrased (3/3)** |
| GPU metrics (observation) | Inconclusive: no GPU metrics exporter | Inconclusive: no GPU metrics exporter |
| Prefix cache (observation) | Pass | Pass |

The vLLM run sent **668 requests in 244 seconds** and the Ollama run **640 requests
in 472 seconds**. Neither run aborted, and the CLI returned 1 for both failed
outcomes. These are endpoint results for these models on this hardware, not
approved deployment baselines.

In the Load test, vLLM failed long/short at concurrency 4 and at 2 requests per
second; short/long at concurrency 1 was inconclusive. Ollama failed long/short at
concurrency 4 and short/long at concurrency 4 and at both arrival rates; short/short
at concurrency 4 and short/long at concurrency 1 were inconclusive. Ollama answered
one request at a time, and Giraffe reported that concurrent correctness was not
tested on it. Across the four short/short conditions together (480 requests on
vLLM, 419 on Ollama), Giraffe reported 8.02 requests per second with a median first
output of 66.8 ms and a median inter-token latency of 15.9 ms for vLLM, and 6.98
requests per second, 67.0 ms and 9.09 ms for Ollama.

Both models answered the `short.copy.v2` fixture with a paraphrase, for example
`The blue box contains seven red cards. Each card has the label "K7P4".` from vLLM,
instead of the expected `The blue box holds seven red cards. The label on each card
is K7P4.` These are answer-check failures of the 1.5B models rather than evidence
that cancellation is broken. Server-side stop stayed unverified. The one timeout
in each run is the check's intentional client-deadline request.

The GPU check reads DCGM exporter metrics. None ran in the notebook, so the check
stayed inconclusive on both engines even though `nvidia-smi` was available. The
prefix check needed vLLM's `--enable-prompt-tokens-details`: in an earlier session
without it, prefix stayed inconclusive with no independent-control cache evidence.

Both runs printed a preflight warning and continued. vLLM returned HTTP 400 to the
non-streamed preflight because `stream_options` from the configuration rides on
non-streamed requests ([#135](https://github.com/0dust/giraffe/issues/135)); a
separate `--nonstream` run with the same configuration failed all 7 of its requests
the same way. Ollama's preflight timed out after 15 seconds while the model was
still loading; the first measured request took about 108 seconds, and endpoint
access passed.

Not exercised: the context, recovery, sessions, multi-user, tools, consistency,
gateway and scale-down checks; SGLang, TensorRT-LLM, LMDeploy, TGI and llama.cpp
server; GPUs other than the T4; and container images.
